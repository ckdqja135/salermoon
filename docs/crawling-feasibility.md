# Vercel 내 상품 수집 전환 검토

## 배포 조건

별도 서버를 운영하지 않고 기존 Next.js 프로젝트를 Git push하여 Vercel에
배포한다. Next.js Route Handler / Vercel Function 사용은 허용한다.
현재 `/api/lowest`와 `/api/image-proxy`도 서버에서 실행되는 구조다.

## 2026-09-13 확인 결과

개발 환경에서 인증 쿠키 없이 공개 페이지에 GET 요청을 보냈다.
Vercel 배포 환경에서의 실측 결과는 아니다.

| 경로 | 관측 결과 |
| --- | --- |
| 쇼핑 검색, `iphone`, 가격순 파라미터 | 네이버 로그인 페이지로 이동. 최종 HTTP 200이지만 상품 HTML이 아님 |
| 쇼핑 검색, `생수`, 최소 파라미터 | HTTP 418, 쇼핑 서비스 접속 제한 안내 |
| 통합검색, `where=shopping`, `생수` | HTTP 200. 내장 쇼핑 상태에 8개 카드: 광고 4개, 프로모션 1개, 일반 카탈로그 3개 |

### 같은 날 추가 검증: 통합검색 다중 페이지 수집 성공

별도 임시 프로필의 실제 Chrome(headless)으로 쇼핑 검색을 렌더링해도 접속 제한
화면을 받았다. 그러나 통합검색 HTML의 쇼핑 초기 상태와 공개 클라이언트에 사용된
`https://ns-portal.shopping.naver.com/api/v2/shopping-paged-slot` 요청을 확인하여,
로그인 없이 추가 상품을 받을 수 있었다. 처음 HTML에 보이는 상품 수가 전부라는
초기 판단은 수정한다.

| 검색어 | 확인 범위 | 반환 카드 수 | 광고·프로모션 제외 상품 카드 | 판매처명·직접 상품 링크를 갖춘 일반 카드 |
| --- | --- | ---: | ---: | ---: |
| 생수 | 1~2페이지 | 16 | 6 | 0 (6개 모두 가격비교 카탈로그) |
| 아이폰 16 | 1~4페이지 | 32 | 20 | 11 |
| 커피 원두 | 1~4페이지 | 32 | 12 | 8 |

2페이지 요청에 1~2페이지, 4페이지 요청에 1~4페이지가 함께 반환되었다.
아이폰은 추가 요청마다 이전 응답에 없던 일반 상품 ID가 각각 8개, 4개,
커피 원두는 각각 3개, 6개 확인되었다. 위 표는 마지막 응답의 카드 수이며,
전체 쇼핑 검색 건수 또는 전체 판매처 수가 아니다. 광고 구성과 순위는 요청 사이에도 바뀌었다.

실제 추출 예: `콩스콩스 원두커피 베트남 로부스타 블루드래곤 워시드G1 1kg 홀빈 원두콩`,
표시 가격 11,900원, 판매처 `콩스콩스`, 직접 상품 링크 확인.
가격은 검색 결과에 표시된 값이며 결제 가격·배송비·재고까지 검증한 것은 아니다.

**판정: 현재 환경에서 통합검색 기반 자동 수집과 다중 페이지 추출은 성공했다.**
일반 상품의 가격·판매처·링크를 기존 분석 기능에 연결할 기술적 경로가 있다.
단, 카탈로그에는 개별 최저가 판매처 이름·직접 구매 링크가 없고 가격비교 링크만
있다. 예를 들어 `생수`는 이 데이터만으로 판매처별 필터를 온전히 복구할 수 없다.
검색 범위(기존 기본 300개), 상위 페이지 한도, 원본 정렬·제외 옵션, 반복 요청 안정성,
Vercel 실행 환경은 검증하지 않았다. 공개 웹 화면의 내부 요청이므로 응답 형식 변경에도 취약하다.

운영 검색에 연결하지 않았으며 로그인 쿠키나 비밀키 없이 검증했다.
외부 JavaScript를 실행하지 않고 Acorn으로 정적 데이터만 해석했다.

## 재확인 명령

Node.js 22 이상, 인터넷 연결이 가능한 환경에서:

```sh
npm run check:shopping-source
npm run check:shopping-source -- "아이폰 16"
npm run check:shopping-source -- "아이폰 16" --deep
node --test scripts/lib/shopping-state.test.mjs
```

상태 코드, 최종 호스트, 페이지 제목, 로그인/차단 여부와 쇼핑 카드 종류별 개수를
출력한다. `--deep`은 실제 상품 필드를 추출하고 2·4페이지 요청에서 새 상품이
반환되는지 확인한다. HTML을 실행하거나 저장하지 않으며 키나 쿠키가 필요하지 않다.
쇼핑 경로가 차단되거나 요청이 실패하면 종료 코드 1을 반환한다.
통합검색 추출이 성공해도 쇼핑 직접 경로가 차단되면 종료 코드는 1이다.
종료 코드 0은 모든 시도에서 오류가 없었다는 뜻이며 기존 기능 복구를
보장하지 않는다. 응답당 15초/3 MB로 제한한다.

## 구현을 진행하기 위한 기준

1. Vercel 실행 환경에서 상품 데이터가 반환되는 수집 경로를 확보한다.
2. 서로 다른 검색어에서 상품명, 실제 판매가격, 판매처, 구매 링크를 검증한다.
3. 페이지 이동, 가격순 정렬, 제외 조건을 검증한다. 광고/프로모션과 일반 상품을 구분한다.
4. 확인된 데이터 형식을 `NaverShopRawItem`으로 변환하여 기존 필터/통계 서비스에 연결한다.
5. 타임아웃, 응답 크기 제한, 캐시, 중복 요청 병합, 차단 응답 처리를 추가한다.
6. Vercel Preview에서 검색과 이미지 저장을 확인한 다음 기존 Git 배포 흐름을 사용한다.

직접 수집이 계속 제한되면 허용된 상품 데이터 API 또는 관리형 수집 서비스를
Vercel Function에서 호출하는 방식이 필요하다. 서비스 선택과 계정/키 확보 전에는
이를 동작하는 대체 경로로 간주할 수 없다.

## 2026-09-13 구현 반영 상태

위 검증 경로가 운영 검색에 연결되었다. 이 문서의 앞부분은 연결 전 검증 기록이다.

- `src/lib/shopping/core.mjs`: 초기 상태·paged-slot 정적 해석, 광고 제외,
  상품 ID 중복 제거, 가격·링크 검증, 제목 마크업 정리 (node --test로 검증)
- `src/lib/shoppingSource.ts`: 요청 조립, 타임아웃/응답 크기 제한,
  차단(418/429/로그인)·결과 없음·형식 변경 구분, 60초 캐시 + 진행 중 요청 병합
- `/api/lowest`: 기존 필터/통계 서비스(`getLowestPrice`, `domain/filtering`)를
  그대로 재사용. 네이버 API 키 검사(`utils/env.ts`)와 오픈 API 클라이언트
  (`lib/naverShopClient.ts`)는 제거됨
- 응답에 `collection` 메타(수집 페이지 수, 광고/카탈로그/일반 카드 수)가 추가되어
  정렬·통계가 수집 범위 내 기준임을 UI에 표시한다
- 검색 1회당 원격 요청은 최대 2회(HTML 1 + 페이지 이동 1). 기본 수집 범위는
  최대인 10페이지(관측상 일반 상품 약 30~80개)로, 기존 API 기본 300개보다 좁다
- 주의: 정상 HTML의 스크립트에도 `captcha` 문자열이 있으므로 차단 감지는
  안내 문구·상태 코드·로그인 리다이렉트만 사용한다 (구현 중 실제 오탐 발생)
- Vercel 배포 환경 실측은 아직 없음. 로컬 `next start` 기준 통합 검증만 완료
